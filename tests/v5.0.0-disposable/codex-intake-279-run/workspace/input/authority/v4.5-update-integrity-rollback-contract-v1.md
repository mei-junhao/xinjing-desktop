# v4.5 Update Integrity and Rollback Candidate Contract v1

This is a task-local frozen contract derived from the XinJing development plan sections 19.3, 19.6, 25.3, 27.1, 27.3 and 27.4, plus `v5.0-development-boundary-v1.md`. It governs only the isolated candidate in Task 279. It does not authorize production integration or release.

## Objective

Prove, in a candidate-local implementation and synthetic runtime rehearsal, that a XinJing update cannot replace a usable installation or corrupt durable user data when feed metadata, artifact bytes, channel, download, installation, migration, first launch, or health verification fails.

## Required invariants

1. The update feed is parsed as typed data. Version, channel, path, URL, byte size, and SHA-512 must be validated before staging. Unknown fields may be ignored only when they cannot change the selected artifact or authority.
2. The artifact bytes being staged must be the exact bytes whose size and SHA-512 appear in the accepted metadata. A missing, malformed, mismatched, or cross-channel artifact fails closed.
3. NSIS installation updates and portable in-place updates are separate strategies. A portable replacement may not silently use the installer artifact, and an installer update may not silently copy over a portable executable.
4. The state machine must distinguish `discovered`, `awaiting-confirmation`, `downloading`, `verified`, `backup-created`, `staged`, `restarting`, `health-check`, `committed`, `failed`, and `rolled-back`. Unknown or out-of-order transitions fail closed.
5. A pre-update safety snapshot is created and verified before any durable migration or executable replacement. A failed snapshot blocks the update and leaves the current installation untouched.
6. The update journal and recovery marker are atomic, bounded, redacted, idempotent, and safe to replay after process termination. They must not contain clinical正文, prompts, API keys, tokens, full paths, or raw provider responses.
7. A failed migration, failed first start, failed health check, interrupted replacement, stale pending marker, or invalid rollback artifact must produce an explicit failure/rollback result. It must not claim success, delete user data, or retry a non-idempotent replacement blindly.
8. Rollback uses a previous known-good artifact and a compatible data strategy. It never rolls back by deleting the user database or by silently discarding newer user data.
9. The user confirmation boundary remains explicit. Checking for an update, downloading, installing, and rolling back have separate states and results; no background update may bypass confirmation or fabricate a success toast.
10. The candidate must retain Free manual data workflows and must not touch commercial, AI, XJSUP, entitlement, or clinical-domain contracts.

## Evidence standard

Source-string checks alone are insufficient. The candidate tests must execute the real candidate module/entry path with a synthetic loopback feed and deterministic fake updater/installer adapter. A real Electron smoke path is required when the frozen environment provides it; if it is unavailable, the report must say `BLOCKED` and preserve the environment evidence.

## Forbidden substitutions

- Do not call the real update URL or COS.
- Do not run a build, pack, installer, signer, upload, publish, or remote manifest update.
- Do not replace the candidate's real update entry with a miniature mock page or a copied handler and call that production evidence.
- Do not accept an old screenshot, old hash, old report, or historical package as current evidence.
- Do not broaden this contract to repair 270, 277, 278, commercial billing, AI, or XJSUP.
